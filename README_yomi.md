# Kindle for macOS の著者名読み調査

## 概要

現行の Kindle for macOS が使用する次のデータベースを対象に、著者名の読みを抽出できるか再調査した。

```text
~/Library/Containers/com.amazon.Lassen/Data/Library/Protected/BookData.sqlite
```

調査の結果、すべての書籍から取得することはできなかったが、シリーズ・グループ情報を利用すると一部の書籍ではカタカナの著者読みを取得できることが分かった。

この調査はデータベースを読み取り専用で開いて行い、既存のプロジェクトファイルおよび Kindle のデータベースには変更を加えていない。

## 旧 Kindle アプリとの違い

旧 Kindle アプリでは、次の XML キャッシュに書籍メタデータが保存されていた。

```text
~/Library/Application Support/Kindle/Cache/KindleSyncMetadataCache.xml
```

この XML では、次のように `author` 要素の `pronunciation` 属性に読みが格納されていた。

```xml
<author pronunciation="サトウ ツトム">佐島 勤</author>
```

現行の Kindle アプリはこの XML を使用していないため、現在の書籍情報を得る目的では利用できない。

## 最初の調査で分かったこと

`ZBOOK` には次の著者関連カラムが存在する。

- `ZDISPLAYAUTHOR`
- `ZSORTAUTHOR`
- `ZALTERNATESORTAUTHOR`

ただし、これらは可読な文字列ではなく BLOB として保存されている。アプリに含まれる Core Data モデルを確認すると、これらの属性には `LassenAppCore.EncryptedStringTransformer` が指定されていた。

アプリ本体からは AES 暗号化・復号および Keychain に関係する処理も確認できた。このため、BLOB は単なるハッシュや内部ソートキーではなく、暗号化された文字列と考えられる。データベースだけを直接読む現在のプログラムからは、復号に必要なキーや変換処理を利用できていない。

また、`ZSYNCMETADATAATTRIBUTES` は `NSKeyedArchiver` 形式の binary plist であり、著者名は復元できるが、著者名の読みは含まれていなかった。

## 再調査で見つかった読み

`ZBOOK` 以外のテーブルを調べたところ、シリーズ・グループ情報を保持する `ZGROUP` に、次の平文カラムが存在した。

- `ZDISPLAYAUTHOR`: 表示用の著者名
- `ZSORTAUTHOR`: カタカナの著者読み
- `ZALTERNATESORTAUTHOR`: 代替ソート用著者名

確認できた例:

```text
清水茜                 -> シミズアカネ
ふじた                 -> フジタ
若木 民喜              -> ワカキ タミキ
井上智徳               -> イノウエトモノリ
米村孝一郎; 森岡浩之  -> ヨネムラコウイチロウ モリオカヒロユキ
梶尾真治; 鶴田謙二    -> カジオシンジ ツルタケンジ
```

`ZBOOK.ZGROUPID` は実データでは使用されていなかった。書籍とグループの対応は、中間テーブル `ZGROUPITEM` を介して取得する。

```sql
SELECT b.Z_PK,
       g.ZDISPLAYAUTHOR,
       g.ZSORTAUTHOR
  FROM ZBOOK AS b
  JOIN ZGROUPITEM AS gi
    ON gi.ZBOOK = b.Z_PK
  JOIN ZGROUP AS g
    ON g.Z_PK = gi.ZPARENTCONTAINER
 WHERE g.ZSORTAUTHOR IS NOT NULL
   AND trim(g.ZSORTAUTHOR) <> '';
```

## 著者名と読みの対応表としての再利用

`ZGROUP.ZDISPLAYAUTHOR` と `ZGROUP.ZSORTAUTHOR` から、著者名と読みの対応表を作ることもできる。

複数著者の分割規則は必ずしも明確ではないため、まず単著のグループだけを使用し、同じ著者名に複数の異なる読みがないものに限定した。その結果、168人分の一意な対応を得られ、矛盾する対応はなかった。

例:

```text
殆ど死んでいる    -> ホトンドシンデイル
藤子・Ｆ・不二雄  -> フジコエフフジオ
畑健二郎          -> ハタケンジロウ
はまじあき        -> ハマジアキ
ゆうきまさみ      -> ユウキマサミ
よしながふみ      -> ヨシナガフミ
```

この対応表を `ZSYNCMETADATAATTRIBUTES` から復元した著者名に適用すると、シリーズに直接関連付けられていない一部の書籍にも読みを補完できる。

## 調査時点の取得件数

調査時点のローカルデータベースでは、結果は次のとおりだった。蔵書や同期状態によって件数は変化する。

- 全書籍: 3,011冊
- 著者情報がある書籍: 3,009冊
- `ZGROUP` との関連から直接読みを取得できた書籍: 1,101冊
- 単著の対応表から追加で全著者の読みを補完できた書籍: 16冊
- 合計: 1,117冊、著者情報がある書籍の約37.1%
- 対応表から一部の著者だけ補完できた複数著者本: さらに7冊

直接取得できる1,101冊と対応表から取得できる書籍には大きな重複があるため、単純にそれぞれの件数を加算してはいけない。

## 特定著者の確認結果

次の読みは、旧 XML では確認できたものの、今回作成した現行DB由来の対応表には存在しなかった。

```text
京極夏彦 -> キョウゴクナツヒコ
佐島 勤  -> サトウ ツトム
```

したがって、この2名については現行DBだけから可読な読みを復元できていない。

## 複数著者本の扱い

複数著者のグループでは、`ZDISPLAYAUTHOR` がセミコロン区切り、`ZSORTAUTHOR` が空白区切りになる例がある。しかし、著者名や読み自体に空白が含まれる可能性があり、両者を常に安全に一対一対応させられるとは限らない。

そのため、次の扱いが安全である。

- 書籍に関連する `ZGROUP.ZSORTAUTHOR` がある場合は、複数著者をまとめた読みとして使用する。
- 著者ごとの対応表を作る場合は、原則として単著のグループだけを使用する。
- 複数著者本で一部の著者しか対応表にない場合は、完全な読みとして出力しない。

## 現時点で考えられる抽出手順

`Pronunciation of Author` を可能な範囲で出力するなら、次の優先順位が考えられる。

1. `ZGROUPITEM` を介して関連付けた `ZGROUP.ZSORTAUTHOR` を使用する。
2. 単著の `ZGROUP.ZDISPLAYAUTHOR` と `ZGROUP.ZSORTAUTHOR` から作った一意な対応表を、書籍の著者名に適用する。
3. 読みを得られなければ空欄にする。

この方法は推定や外部辞書による読み生成ではなく、現在の Kindle データベース内に平文で保存されている情報だけを再利用する。ただし、シリーズ情報がない著者には適用できない。

`listKindleBooks2` では `-y` を指定したときだけこの手順で `Pronunciation of Author` を補完する。`-y` を指定しない場合、および信頼できる読みを取得できない場合は、このフィールドを空欄にする。

## 未解決事項

- `ZBOOK.ZSORTAUTHOR` などの暗号化カラムを、Kindle アプリのキーと同じ条件で安全に復号する方法
- `ZSERIESAUTHOR` に定義されている `authorPronunciation` が、実データでは空テーブルになっている理由
- 複数著者の表示名と読みを確実に個別対応させる規則
- シリーズ情報を持たない書籍の著者読みを、現行DBだけから取得する方法

現時点の結論は、「現行DBに著者読みがまったく存在しない」のではなく、「`ZBOOK` の著者読みは暗号化されているが、`ZGROUP` に保存されたシリーズ著者の読みは平文で利用できる」である。
